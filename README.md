# Imprenta Collantes · sistema de gestión

Aplicación ASP.NET Core 8 para administrar clientes, proveedores y productos; emitir cotizaciones, confirmar ventas, seguir los trabajos del taller y consultar analítica operativa. Incluye un asistente opcional de pre-cotización conectado a Groq.

## Ejecutar el entorno local configurado

Se requiere el runtime ASP.NET Core 8 y una instancia SQL Server. La configuración local del proyecto apunta a `Server=.;Database=imprentacollantesbd`; no contiene contraseñas y supone que la instancia predeterminada de SQL Server está instalada y ejecutándose. Desde Visual Studio Code puedes iniciar el perfil `http` con la extensión C#; también puedes usar desde la raíz:

```sh
dotnet run --project ProyectoFinal/ProyectoFinal.csproj --launch-profile http
```

Abre `http://localhost:5092`. La base actual ya contiene `admin@admin.com` con el rol `Admin`; el secreto de bootstrap no está configurado ni se necesita para iniciar. La contraseña antigua por defecto debe cambiarse antes de usar el sistema con información sensible. Nunca guardes contraseñas en `appsettings.json`.

**Base actual (`imprentacollantesbd`):** se respaldó antes de los cambios en `C:\Program Files\Microsoft SQL Server\MSSQL16.MSSQLSERVER\MSSQL\Backup\imprentacollantesbd_pre_migration_20261022.bak` y se verificó con `RESTORE VERIFYONLY`. Como las tablas comerciales ya existían, se agregó su baseline `20261022042127_AddBusinessTables` al historial luego de comprobar el esquema y crear los 10 índices FK faltantes. Después se aplicó `20261022190105_WidenIdentityKeyColumns` para ampliar las claves de Identity. `AddBusinessTables` crea las tablas comerciales solo en una base nueva. No ejecutes migraciones automáticamente al arrancar.

**Ventas y taller en la base local:** antes de aplicarlas se creó y verificó el respaldo `C:\Program Files\Microsoft SQL Server\MSSQL16.MSSQLSERVER\MSSQL\Backup\imprentacollantesbd_pre_ventas_taller_20261023.bak` (`COPY_ONLY`, `CHECKSUM`, `RESTORE VERIFYONLY`). Ya están aplicadas `20261022214724_VentasTallerYPermisos` (ventas, taller, tipos, auditoría y permisos) y `20261023135013_StockConcurrency` (control de concurrencia de productos). La migración de ventas identifica por relación el nombre real de la FK heredada en `DetallePedido`. No ejecutes `AddBusinessTables` nuevamente ni apliques estas migraciones a otra base existente sin revisar y conciliar su esquema e historial. **Los dos productos existentes son artículos y deben mantenerse como tales.**

**Analítica y costos en la base local:** antes de aplicarlos se creó y verificó con `RESTORE VERIFYONLY` el respaldo `C:\Program Files\Microsoft SQL Server\MSSQL16.MSSQLSERVER\MSSQL\Backup\imprentacollantesbd_pre_bi_costos_20261023_232138.bak` (`COPY_ONLY`, `CHECKSUM`). Está aplicada `20261024041212_AddHistoricalCosts`, que agrega columnas de costo opcional (sin IGV) a `Producto` y `DetalleVenta`, sin rellenar ni cambiar productos o ventas existentes. Ambos artículos conservan costo `NULL` hasta que un usuario ingrese su precio de compra real; no atribuyas costos a ventas anteriores sin registros históricos verificables. El flujo de ventas, la captura histórica del costo y el panel de analítica con autenticación Admin se probaron también mediante HTTP contra una base temporal SQL Server, que se eliminó tras la prueba.

**Otra base de datos existente:** no ejecutes `dotnet ef database update` hasta verificar su esquema, respaldarla y conciliar las filas de `__EFMigrationsHistory`. Una base con tablas comerciales ya creadas necesita baseline, no la migración `AddBusinessTables` ejecutada de nuevo.

**Clientes, proveedores y catálogos:** se aplicó `20261029031316_CustomerSupplierCatalogs` tras respaldo verificado. Los catálogos de MySQL `facturuna` se copiaron a SQL Server como `ubigeo` (2 088 filas) y `documentoidentidad_tipo` (6 filas), conservando la jerarquía y la codificación. Los dos clientes antiguos conservaron su DNI; los proveedores antiguos no recibieron datos ficticios. Consulta el [procedimiento de importación y las reglas de captura](Documentacion/IMPORTAR_CATALOGOS_FACTURUNA.md). No apliques ni importes ciegamente en otra base poblada.

**Inventario físico activado en la base local:** `20261029042715_PhysicalInventoryActivation` preparó «Almacén principal», unidad base «UNIDAD (BIENES)» y presentación «Unidad». Un operador aprobó el conteo real; desde entonces ventas descuentan del nuevo `Stock` al confirmar y cancelaciones lo restituyen. El stock heredado no se copió como apertura. Para otras bases el conteo sigue siendo una acción manual obligatoria. Consulta [procedimiento y respaldo](Documentacion/INVENTARIO_ESQUEMA.md).

## Límites actuales

- La cuenta registrada públicamente no recibe roles automáticamente. Un administrador debe asignarle un rol y configurar su acceso desde «Usuarios», «Roles» y «Permisos de menú».
- Las cotizaciones admiten productos, cantidades y precios por línea. El servidor calcula subtotal, IGV del 18% y total. La vigencia predeterminada es siete días desde la emisión en fecha peruana; las vencidas se revalidan con revisión humana creando una cotización nueva vinculada. **Administración → Series internas** permite configurar serie, próximo correlativo y dígitos por tipo; las series iniciales son `C001-004532` para cotización y `V001-004532` para venta interna. Los documentos ya emitidos mantienen su numeración. Ambas se pueden imprimir en A4; la venta imprimible **no es un comprobante de pago tributario**. Consulta [alcance y preparación para una futura fase SUNAT](Documentacion/DOCUMENTOS_COMERCIALES_INTERNOS.md).
- Al confirmar una cotización vigente se crea una **Venta** y un **Pedido de taller** asociado en una sola transacción. Se valida y descuenta el stock de artículos; los servicios no usan inventario. Si falta stock, la confirmación completa se rechaza. La venta se puede cancelar y reponer stock solo mientras el trabajo siga `En cola`. Los cambios simultáneos entre cancelación e inicio del taller se resuelven por estado; la edición de productos usa `rowVersion` para detectar stock desactualizado.
- El taller avanza los trabajos en secuencia: `En cola` → `En impresión / acabado` → `Listo para recojo` → `Entregado`. Las tablas `MenuSistema` y `PermisoRolMenu` relacionan módulos con roles; el administrador puede configurar permisos por operación. El rol `Admin` conserva acceso total. El historial de cotizaciones, ventas y trabajos solo es visible para `Admin`.
- El administrador dispone de «Analítica»: filtra ventas **confirmadas** por fecha de confirmación en horario peruano (UTC−5), presenta ventas **con IGV** separando neto e IGV, excluye las canceladas y compara productos y clientes por importe. Cotizaciones se agrupan por fecha de emisión; taller y alertas de inventario muestran el estado **actual**. El costo unitario sin IGV (compra para artículos, estimación para servicios) es opcional y se copia a cada línea cuando se confirma una venta. La utilidad estimada se calcula sin IGV únicamente para líneas con costo; se etiqueta **parcial** si faltan costos. No representa utilidad neta contable ni facturación tributaria.
- En «Nueva cotización» se puede abrir «Preparar desde solicitud con IA». Requiere el permiso **crear** del menú Cotizaciones. Primero se ocultan automáticamente identificadores frecuentes y **el usuario debe revisar y aprobar el texto exacto que se enviará a Groq**: no es posible identificar infaliblemente nombres o direcciones en texto libre. No se envían datos de clientes ni catálogo. La respuesta se valida y solo se vincula automáticamente un nombre de producto si coincide de forma exacta y única; el usuario selecciona cliente y productos, revisa cantidades y pasa al formulario normal, donde los precios salen del catálogo y pueden corregirse. No se guarda nada hasta «Guardar cotización». Si no hay API key, hay error, respuesta inválida o el servicio demora más de 5 segundos, sigue disponible la cotización manual. El envío está limitado a cinco solicitudes por usuario por minuto. No se guardan mensajes ni respuestas de IA.
- Al cargar el borrador asistido se muestran **referencias locales**, no generadas por Groq: mínimo por unidad sin IGV para un margen bruto del **10 %**, descuento máximo respecto del precio de catálogo cuando existe costo, y última venta confirmada del mismo cliente y producto. Solo se propone evaluar repetir el precio histórico si el nuevo tiraje no es menor y el precio está entre el mínimo y el catálogo; especificaciones y circunstancias pueden diferir. No se aplica automáticamente ninguna referencia. El mínimo se redondea **hacia arriba** al céntimo: un costo de S/ 100 exige S/ 111,12 sin IGV. Con costo ausente o cero no se calcula descuento ni mínimo; con costo conocido el servidor rechaza cotizaciones por debajo del mínimo y vuelve a validarlas al confirmar la venta. Los costos de los dos artículos originales siguen sin registrar; no se inventan costos históricos.
- El envío de correos es simulado (`FakeEmailSender`); no hay envío real ni generación de PDF. La recuperación por correo tampoco está disponible.
- `dotnet build ProyectoFinal.sln` compila la aplicación y `dotnet test ProyectoFinal.sln` ejecuta las pruebas regulares con EF InMemory. Para probar también las migraciones y la carrera cancelación/inicio con SQL Server real, establece `PROYECTOFINAL_SQL_TEST_CONNECTION` con una conexión a `master` y ejecuta `dotnet test ProyectoFinal.Tests/ProyectoFinal.Tests.csproj --filter FullyQualifiedName~SqlServerWorkflowTests`. Esta prueba crea y elimina únicamente una base temporal con nombre aleatorio.

## Configurar Groq (opcional)

Sigue la [guía paso a paso para configurar la API key de Groq](Documentacion/CONFIGURAR_GROQ_API_KEY.md) fuera del repositorio, sin pegar la clave en el chat ni en el historial de la terminal. El modelo predeterminado es `openai/gpt-oss-20b`, compatible con salida JSON Schema estricta; puede cambiarse mediante `Groq:Model` solo por otro modelo compatible. La aplicación nunca envía la clave al navegador. **Sin clave, el asistente avisa y se puede cotizar manualmente.** Antes de usar datos reales revisa las políticas de privacidad aplicables al envío de texto revisado a un tercero.

## Planificación propuesta

El plan acordado queda así:

1. **Reglas operativas:** definidas para vencimiento de cotizaciones, conversión única, stock, cancelación, estados del taller, permisos y auditoría.
2. **Ventas, taller e inventario:** implementados y migrados en la base SQL local; probados con EF InMemory y con una base temporal SQL Server. Los dos productos existentes están correctamente clasificados como artículos.
3. **BI:** panel de analítica y costos históricos implementado, migrado en la base local y probado con EF InMemory y una base temporal SQL Server. El indicador se llama «ventas confirmadas», no «facturado»; se agrupa por fecha de confirmación y se muestra con IGV. Registrar los costos reales de los dos artículos permitirá calcular utilidad de nuevas ventas; no se inventan costos anteriores.
4. **IA y precios:** pre-cotización asistida con Groq, revisión humana, anonimización previa y alternativa manual implementadas y probadas con un proveedor simulado. La llamada real requiere una API key que debe configurar el responsable del entorno. Se implementaron referencias de precio y límites de descuento locales con margen bruto mínimo del 10 % sobre precio sin IGV, costo conocido e historial confirmado del cliente; no existe optimización predictiva de cierre ni recomendación de Groq sobre precios. La IA no inventa precios ni altera los precios del catálogo.

PDF y envío real de correo no forman parte de esta secuencia priorizada; deberán planificarse como alcance separado si se requieren.
